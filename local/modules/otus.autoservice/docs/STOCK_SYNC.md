# Ежедневная синхронизация внешних остатков

> Назначение файла: описывает запуск, штатное применение количества, журналирование, мониторинг и проверку синхронизации версии `0.12.0`.

## Назначение и граница этапа

Синхронизация ежедневно получает у настроенного поставщика текущее абсолютное количество каждой запчасти автосервиса, применяет его к настроенному складу Bitrix и сохраняет проверенный результат в журналы модуля. Значение `6` означает «во внешней системе сейчас 6 единиц», а не изменение на 6 единиц.

Версия `0.12.0` завершает этап 5.17: остаток изменяется только штатными API и считается успешным после контрольного чтения. Заявка на закупку при нулевом остатке пока не создаётся — это этап 5.18.

## Участники процесса

1. `tools/sync_stock.php` загружает CLI-пролог, проверяет миграции и передаёт управление сервису.
2. `StockSyncService` управляет блокировкой, жизненным циклом запуска, порциями и транзакциями журнала.
3. `SparePartStockRepository` читает активные простые товары строго из настроенного CRM-каталога.
4. Непустое значение созданного модулем свойства артикула отличает запчасть от обычного товара CRM-каталога.
5. `StockProviderFactory` выбирает `random_org` или `fake` по настройке модуля.
6. `StockBatchFetcher` превращает ответ или ожидаемую ошибку поставщика в отдельный результат товара.
7. `SyncRunTable` и `SyncItemTable` сохраняют итог запуска и поштучные результаты.
8. `StockQuantityUpdaterInterface` отделяет оркестратор от способа записи и позволяет диагностике не менять каталог.
9. `StockQuantityService` выбирает прямой D7 API либо складской документ по фактическому режиму `State::isUsedInventoryManagement()`.

Репозиторий запрашивает товары D7-выборкой по возрастающему ID. Свойство артикула загружается одним массовым вызовом на порцию; запросов свойства внутри цикла товаров нет. Обычные товары без артикула продвигают курсор, но не отправляются поставщику и не попадают в журнал.

## Последовательность одного запуска

1. Проверить инициатора и размер порции.
2. Проверить, что модуль включён, обязательные модули загружены, миграции применены, таблицы и каталог готовы.
3. Создать поставщика по настройке.
4. Получить именованную блокировку СУБД `otus.autoservice.stock_sync`.
5. Пометить `failed` предыдущие записи `running`, heartbeat которых старше двух часов.
6. Создать строку запуска со статусом `running`.
7. Выбрать очередную порцию товаров и сформировать проверенные `StockItem`.
8. Выполнить внешние HTTP-запросы вне транзакции базы данных.
9. Для каждого успешного ответа применить именно полученное абсолютное количество штатным способом.
10. Повторно прочитать товар и склад и подтвердить целевой остаток и согласованность.
11. Для успешной позиции сохранить изменение каталога, её аудит и счётчики одной транзакцией; ошибку сохранить отдельной короткой транзакцией.
12. Обновить heartbeat после каждой просканированной порции, включая порцию без запчастей.
13. Завершить запуск статусом `completed` либо `completed_with_errors`.
14. Только при полном успехе обновить настройку `stock_sync_last_success_at`.
15. В блоке `finally` освободить именованную блокировку.

Неожиданная инфраструктурная или программная ошибка после создания запуска переводит его в `failed` с безопасным общим сообщением. Исходное исключение возвращается CLI или административной странице. Ошибка до создания строки, например занятая блокировка, не создаёт ложный запуск.

## Таблицы журналов

### `b_otus_autoservice_sync_run`

Одна строка соответствует одному плановому или ручному запуску:

- `PROVIDER_CODE` — код фактически выбранного поставщика;
- `INITIATOR` — `cli` или `admin`;
- `STATUS` — жизненный цикл запуска;
- `TOTAL_ITEMS`, `SUCCESS_ITEMS`, `FAILED_ITEMS` — согласованные счётчики;
- `STARTED_AT`, `HEARTBEAT_AT`, `FINISHED_AT` — начало, признак активности и завершение;
- `ERROR_MESSAGE` — безопасная общая ошибка без ответа поставщика и секретов.

Статусы запуска:

- `running` — обработка ещё выполняется;
- `completed` — все запчасти обработаны успешно;
- `completed_with_errors` — запуск завершён, но есть ошибки отдельных товаров;
- `failed` — запуск прерван общей ошибкой либо признан зависшим.

### `b_otus_autoservice_sync_item`

Одна строка соответствует одной запчасти одного запуска:

- `RUN_ID` и `PRODUCT_ID` связывают результат с запуском и товаром;
- `EXTERNAL_ID` и `ARTICLE` фиксируют использованные внешние идентификаторы;
- `STATUS` равен `success` или `failed`;
- `EXTERNAL_QUANTITY` хранит успешно полученный абсолютный остаток;
- `STORE_ID` указывает склад, к которому применялось количество;
- `APPLY_MODE` равен `direct_api` либо `inventory_document`;
- `PREVIOUS_STORE_QUANTITY`, `APPLIED_STORE_QUANTITY` фиксируют физический остаток до и после;
- `PREVIOUS_PRODUCT_QUANTITY`, `APPLIED_PRODUCT_QUANTITY` фиксируют доступное количество товара до и после;
- `DOCUMENT_ID` содержит ID проведённого складского документа или `null`, если документ не требовался;
- `ERROR_TYPE`, `ERROR_MESSAGE`, `RETRYABLE` описывают безопасную ожидаемую ошибку;
- `DATE_CREATE` фиксирует время записи результата.

Ссылка на будущую заявку закупки будет добавлена этапом 5.18. Прямых внешних ключей СУБД нет: порядок удаления и дальнейшая политика хранения контролируются модулем.

## Способы применения количества

При выключенном складском учёте сервис:

1. Читает резерв выбранного склада и отклоняет внешний остаток меньше резерва.
2. Через `StoreProductTable::add/update` задаёт абсолютный физический остаток склада.
3. Через `Bitrix\Catalog\Model\Product::update` задаёт доступное количество как сумму `AMOUNT - QUANTITY_RESERVED` всех активных складов.
4. Выполняет обе операции одной транзакцией и проверяет каждый ORM `Result`.
5. Повторно читает данные и вызывает общую проверку согласованности каталога.

При включённом складском учёте прямое изменение количества запрещено. Положительная разница оформляется документом `TYPE_STORE_ADJUSTMENT`, отрицательная — `TYPE_DEDUCT`; документ и его позиция создаются штатным API `CCatalogDocs::add`, после чего документ проводится `CCatalogDocs::conductDocument` и отдельно проверяется его статус. Положительный приход использует текущую закупочную цену товара с переводом в базовую валюту. Ненулевая цена без корректной валюты отклоняется; при включённом партионном учёте также отклоняется нулевая цена, чтобы не создать партию с ложной нулевой себестоимостью. Создание, проведение, контрольное чтение и запись успешного аудита выполняются общей транзакцией. Нулевая разница не создаёт пустой документ.

Для ручного административного запуска ответственным документа становится текущий активный пользователь. Для CLI/cron нужно указать ID активного пользователя в поле «Ответственный складских документов (ID)» настроек модуля. Модуль не создаёт этого пользователя автоматически.

## Ручной запуск

Проверить инфраструктуру без записи:

```powershell
php local/modules/otus.autoservice/tools/check_stock_sync.php
```

Выполнить синхронизацию с текущим поставщиком и порцией по умолчанию:

```powershell
php local/modules/otus.autoservice/tools/sync_stock.php
```

Явно передать корень портала и размер сканируемой порции:

```powershell
php local/modules/otus.autoservice/tools/sync_stock.php D:/ospanel6/home/otus.local --batch-size=20
```

Только восстановить зависшие запуски, не обращаясь к поставщику:

```powershell
php local/modules/otus.autoservice/tools/sync_stock.php --recover-stale-only
```

Допустимый размер порции — от `1` до `100`. CLI отказывается начинать рабочий запуск при неприменённых миграциях, чтобы плановое задание не меняло схему неожиданно.

Коды завершения:

- `0` — полный успех либо отсутствие зависших записей при отдельной проверке;
- `2` — обработка завершена с ошибками отдельных товаров либо обнаружен и переведён в `failed` хотя бы один зависший запуск;
- `1` — общая ошибка конфигурации, блокировки, инфраструктуры или программы.

## Настройка cron

Cron не создаётся установщиком, потому что путь к PHP, корень портала, пользователь ОС и система мониторинга зависят от окружения. Пример ежедневного запуска в 02:15 на Linux:

```cron
15 2 * * * /usr/bin/php /home/bitrix/www/local/modules/otus.autoservice/tools/sync_stock.php /home/bitrix/www
```

Задание должно выполняться пользователем ОС, который имеет доступ к файлам портала и использует ту же PHP-конфигурацию, что и Bitrix. Не следует запускать второй экземпляр для того же портала: сервис отклонит его по именованной блокировке.

Для локального Windows-сервера аналогичную команду добавляют в Планировщик заданий Windows, указывая полный путь к `php.exe`, скрипту и корню портала.

## Административный запуск и мониторинг

На административной странице состояния показываются:

1. Код настроенного поставщика.
2. Дата последнего запуска со статусом `completed`.
3. Последний запуск, его статус, счётчики, начало, heartbeat и время завершения.
4. Готовность миграции, каталогов и таблиц.

Пользователь с правом записи на модуль может нажать кнопку ручной синхронизации. POST-запрос защищён сессионным токеном Bitrix и вызывает тот же `StockSyncService`, поэтому параллельный cron и ручной запуск не выполняются одновременно.

Для внешнего мониторинга следует считать ошибкой:

- код CLI `1` или `2`;
- последний статус `failed` или `completed_with_errors`;
- отсутствие нового полного успеха более допустимого для проекта интервала;
- `running` с heartbeat старше двух часов.

Ежедневный рабочий запуск сам восстанавливает устаревший `running`. Команда `--recover-stale-only` предназначена для отдельной проверки мониторинга и не получает внешние остатки: она возвращает `2`, если восстановила хотя бы одну зависшую запись, и `0`, если таких записей нет.

## Диагностика с записью

Полный очищаемый тест запускается только явно:

```powershell
php local/modules/otus.autoservice/tools/check_stock_sync.php --write-test
```

Он выполняет следующие проверки:

1. Полностью успешный запуск через `FakeStockProvider`.
2. Продолжение порции после одной типизированной временной ошибки поставщика.
3. Продолжение порции после одного ошибочного `Result` применителя остатка.
4. Перевод искусственно устаревшего `running` в `failed`.
5. Распространение неожиданной программной ошибки и очистку запуска, ID которого сервис не вернул.
6. Отклонение нереалистичной будущей даты последнего полного успеха.
7. Полный контракт успешного применителя и заполнение новых полей поштучного журнала.
8. Неизменность `ProductTable::QUANTITY` всех обнаруженных запчастей благодаря внедрённому fake-применителю.
9. Отклонение успешного `Result`, в котором движение в режиме складского документа не содержит `DOCUMENT_ID`.
10. Удаление только созданных диагностикой строк и восстановление прежней глобальной даты последнего успеха.

Режим записи отказывается работать, если уже существует активный запуск, и требует хотя бы одну запчасть с внешним ID и артикулом.

Реальный прямой D7 API проверяется отдельной обратимой командой:

```powershell
php local/modules/otus.autoservice/tools/check_stock_quantity.php --write-test
```

Она разрешена только при выключенном складском учёте, временно увеличивает целочисленный остаток одной запчасти на единицу, проверяет успешный `Result`, затем намеренно выбрасывает исключение из callback аудита и подтверждает откат второго изменения. В `finally` команда возвращает исходные количества товара и склада и ещё раз подтверждает согласованность. При включённом складском учёте безопасная команда остаётся только читающей: тест документов следует проводить на отдельном тестовом портале, потому что проведённые документы являются материальным аудитом и не должны создаваться диагностикой на рабочей базе.
